# Спайк: конвейер оригинальных 3D-ассетов Ancient Strategy (Blender → glb → Godot)

Рабочая папка на сервере: `/opt/asg-art` (не git-репозиторий, результаты забирает координатор).
Все скрипты и рендеры лежат в `/opt/asg-art/scripts` и `/opt/asg-art/out` соответственно.

**Правило Р97 (владелец): все модели — на 100% процедурная генерация собственными скриптами.**
Ни одна геометрия, текстура или материал не заимствованы: вся геометрия построена
примитивами `bpy`/`bmesh` (цилиндры, конусы, боксы, icosphere, ручной bmesh для фронтона
храма), все материалы — процедурные шейдерные графы Blender (шум Noise Texture, ColorRamp,
Pointiness, Mapping/Tex Coord), без единого внешнего изображения-текстуры. Источник
каждого элемента ассетов, перечисленных ниже, — «собственная процедурная генерация»,
других источников нет.

## Окружение сервера (проверено)

- Blender **5.0.1** (headless, `blender -b`), **GPU отсутствует**.
- Cycles: рендер-девайс только `CPU` (AMD Ryzen 9 7950X3D, но контейнеру выделено
  **4 vCPU** — `nproc` = 4, а не 16 физических ядер хоста).
- ImageMagick (`convert`/`magick`) — для контактного листа.
- Python 3.14.4 c Pillow/NumPy/OpenCV (в системном Python; `bpy` живёт только внутри
  Blender, не как отдельный модуль — `python3 -c "import bpy"` не работает, это ожидаемо).
- Godot **4.7.2.stable.mono** (`/usr/local/bin/godot`), headless-импорт работает.

### Выбор движка рендера (замер `scripts/test_render.py`, тестовая сцена 256×256)

| Движок | Время | Годится для «бронзовой фигурки»? |
|---|---|---|
| `BLENDER_WORKBENCH` | ~1.2 с | Нет — студийное освещение — matcap-приближение, металлик/roughness почти не влияют на вид. Годится только для быстрого превью силуэта. |
| `CYCLES` (device=CPU) | ~0.45 с (32 spp, тривиальная сцена) | **Да** — честный Principled BSDF, металлик+патина видны корректно. Выбран как основной движок. |
| `BLENDER_EEVEE` (legacy, GPU нет) | ~27 с + поток `EGL_BAD_MATCH` в stderr | Работает через программный растеризатор (llvmpipe), но на порядок медленнее Cycles на этой же сцене и шумит ошибками EGL в лог. **Не рекомендуется** без GPU — ровно то предупреждение, которое было в задании. `BLENDER_EEVEE_NEXT` в этой сборке Blender 5.0.1 недоступен вовсе (`enum "BLENDER_EEVEE_NEXT" not found`). |

Итог: все финальные рендеры сделаны **Cycles, device=CPU, 64 сэмпла, 512×512**,
с денойзером (`use_denoising=True`). Свет — три солнца (рисующий/заполняющий/контровой)
+ мягкий серый мир, без HDRI-картинок (тоже процедурно).

## Что сгенерировано

Все скрипты лежат в `/opt/asg-art/scripts`, результаты — в `/opt/asg-art/out`.
Общая библиотека частей/материалов/камер/рендера/экспорта — `common.py`.

### 1. `gen_figure.py` — фигурки воинов

```
blender -b -P gen_figure.py -- --type hoplite --culture hellenic --out /opt/asg-art/out
```

Параметры: `--type` (hoplite|legionary|punic_infantry|numidian_cavalry) — пресет культуры/
снаряжения; `--culture`, `--helmet` (corinthian|attic|montefortino|pileus|none),
`--shield` (hoplon|scutum|pelta|none), `--weapon` (spear|sarissa|pilum|sword), `--cloak` (0/1),
`--color` (hex цвета нации на щите/плаще) переопределяют пресет; `--engine`, `--samples`,
`--res`, `--budget` (лимит треугольников, по умолчанию 800), `--seed`, `--out`.

Библиотека частей: тело (торс/ноги/руки/пояс/шея/голова — низкополигональные примитивы),
4 шлема, 3 щита, 4 типа оружия, плащ (изогнутая плоскость), отдельная параметрическая
часть — конь (для конницы), собранный из направленных сегментов (корпус→шея→голова,
методом «цепочки направлений», см. ниже).

Материал «бронзовая фигурка»: единый процедурный shader на весь силуэт — металлик 0.92,
патина (зеленоватый оттенок) сгущается во впадинах через `Geometry → Pointiness`,
промодулирована шумом Noise Texture, — а не заливка одним цветом. Цвет нации — отдельный
матовый материал только на щите и плаще (по ТЗ).

| Вариант | Треугольников | Размер .glb |
|---|---:|---:|
| Гоплит эллинский (коринфский шлем, гоплон, копьё, плащ) | 428 | 23 032 байт |
| Легионер римский (монтефортино, скутум, пилум, плащ) | 428 | 23 316 байт |
| Пунийский пехотинец (пилос, пельта, копьё, без плаща) | 316 | 18 180 байт |
| Нумидийский всадник (без шлема, пельта, копьё, конь отдельной частью) | 504 (292 всадник + 212 конь) | 25 680 байт |

Все варианты укладываются в лимит 800 тр. на фигуру (и конь отдельно — тоже мимо лимита
не вышел, хотя бюджет на него формально не оговорён — я применил тот же потолок).

### 2. `gen_ship.py` — корабли

```
blender -b -P gen_ship.py -- --type trireme --sail raised --out /opt/asg-art/out
blender -b -P gen_ship.py -- --type merchant --sail furled --out /opt/asg-art/out
```

Параметры: `--type` (trireme|merchant), `--sail` (raised|furled), `--color` (цвет паруса/
окантовки), плюс общие `--engine/--samples/--res/--budget(1200)/--seed/--out`.

Корпус — сплюснутый конус (уплощение именно поперечного сечения, не длины — на первой
версии перепутал ось масштабирования, из-за чего корпус рендерился неприплюснутым
конусом-«торпедой»; после разбора в этом README сохранено как пример реальной ошибки,
см. раздел «Проблемы» ниже). Трирема: бронзовый таран, три ряда вёсел упрощены плоскими
рёбрами по бортам (честные отдельные вёсла увели бы бюджет за тысячи треугольников),
кормовой помост, рулевое весло, мачта+парус (поднят/скатан параметром). Торговое судно:
широкий округлый корпус, планширь, мачта+парус, рулевое весло, без тарана и вёсел.

| Вариант | Треугольников | Размер .glb |
|---|---:|---:|
| Трирема (парус поднят) | 246 | 14 432 байт |
| Торговое судно (парус поднят) | 186 | 10 188 байт |

Оба варианта далеко внутри лимита 1200.

### 3. `gen_building.py` — постройки

```
blender -b -P gen_building.py -- --type temple --columns 4 --out /opt/asg-art/out
blender -b -P gen_building.py -- --type wall --level 2 --out /opt/asg-art/out
blender -b -P gen_building.py -- --type lighthouse --out /opt/asg-art/out
```

Параметры: `--type` (temple|wall|lighthouse), `--columns` (число колонн по фасаду храма,
периметр достраивается пропорцией периптера), `--level` (1..3, высота стены/башни/крыши
только для wall), `--color` (флаг на стене), плюс общие `--engine/--samples/--res/
--budget(1500)/--seed/--out`.

- **Храм-периптер**: стилобат, кольцо колонн по периметру (параметр `--columns` — число
  колонн по короткому фасаду, боковой ряд считается пропорцией `+2`), антаблемент,
  двускатная крыша, треугольные фронтоны (честная bmesh-призма, не хак через N-угольный
  конус — см. «Проблемы»).
- **Стена с башней**: зубчатая стена, круглая башня с зубцами и конической крышей,
  флаг цвета нации (появляется с уровня 2), ворота. `--level` управляет высотой стены/
  башни и добавляет флаг.
- **Маяк**: три сужающихся яруса (квадратное основание → восьмигранник → цилиндр),
  фонарная камера на колоннах, коническая крыша, светящееся пламя (Emission-материал).

| Вариант | Треугольников | Размер .glb |
|---|---:|---:|
| Храм-периптер (4 колонны по фасаду) | 640 | 32 788 байт |
| Стена с башней (уровень 2) | 334 | 19 160 байт |
| Маяк | 248 | 14 500 байт |

Все — далеко внутри лимита 1500.

## Проверка импорта в Godot

Минимальный проект создан в `/opt/asg-art/godot_probe` (`project.godot`,
рендерер `gl_compatibility` — единственный, гарантированно работающий без GPU/Vulkan).
Все 9 `.glb` скопированы в проект, запущено:

```
godot --headless --path /opt/asg-art/godot_probe --import
```

**Результат: все 9 файлов импортированы без ошибок** — для каждого создана пара
`.import` + `.godot/imported/*.scn`. Полный лог см. в отчёте координатору.

## Проблемы, найденные и исправленные в процессе (для истории/повторного использования)

1. **Материал патины заливал всю модель ровным цветом.** Два линка на один сокод
   `Fac` в `MixRGB` (Pointiness и шум) — Blender молча оставляет только последний
   линк. Исправлено: `Pointiness` инвертируется и перемножается с шумом в отдельном
   узле `Math`, и уже это идёт в `ColorRamp → MixRGB.Fac`.
2. **Плащ лежал плашмя, а не свисал за спиной.** Поворот плоскости был на 8°, нужно
   было ~90°+8° — по умолчанию `make_plane` лежит нормалью вверх (как пол).
3. **Наездник «парил» над конём.** Высота посадки (`ground_z=1.62`) не была
   согласована с реальной высотой спины коня (~1.3). Исправлено через общую
   константу `HORSE_BACK_Z` и отдельную (не «от земли») сборку ног всадника для
   `mounted=True`.
4. **Шея/голова коня были геометрически оторваны от корпуса** (видно на
   промежуточном рендере как «летающие обломки»). Причина — координаты каждой
   части подбирались на глаз независимо, без анализа стыков. Исправлено полным
   переходом на «цепочку направленных сегментов»: каждый следующий сегмент
   стартует ровно в точке-наконечнике предыдущего (`add_segment()` возвращает
   `tip`, вычисленный по формуле поворота, а не подбирается вручную).
5. **Корпус корабля не сплющивался в корпус лодки, а оставался острым конусом.**
   Масштаб применялся к локальной оси Z (длина) вместо локальной Y (поперечное
   сечение, которое после поворота на −90° по X становится мировой вертикалью).
   Дополнительно исходная осадка была почти равна радиусу борта — даже с
   правильной осью эффект был бы почти не виден. Исправлено: верная ось
   масштабирования + осадка ≈ 0.3–0.35 от полуширины борта.
6. **Фронтон храма рендерился гигантским плоским диском**, закрывающим половину
   сцены. Хак «N-угольный конус с 3 сегментами» даёт треугольник, вписанный в
   окружность радиуса `r2`, — при `r2 = половина ширины храма` получается
   треугольник, кратно больше самого здания. Исправлено честной bmesh-призмой
   (`make_pediment`) с явно заданными шириной/высотой/толщиной.

Держите это в голове при доработке: подобные ошибки (перепутанные оси после
поворота, два линка в один сокет шейдера, координаты «на глаз» вместо
геометрического вывода) — системный риск процедурной генерации в bpy, а не
случайность этого конкретного прогона.

## Что НЕ получилось / ограничения без GPU и в рамках спайка

1. **Критично: процедурные (нодовые) материалы не переживают экспорт в glTF.**
   Проверено на всех типах ассетов (`figure_hoplite.glb`, `ship_trireme.glb`,
   `building_temple.glb`) — материалы `Бронза_патина`, `Дерево`, `Камень_мрамор`
   экспортировались **без `baseColorFactor`** (в спецификации glTF это откатится
   к белому по умолчанию), потому что Base Color/Roughness у них подключены через
   узлы (Noise → ColorRamp → MixRGB), а не заданы статичным значением сокета.
   Экспортер glTF умеет вытащить только «плоские» PBR-параметры. Материалы,
   заданные напрямую (`Цвет_нации`, `Парус_цвет` — просто `default_value` без
   линков), экспортировались корректно, с `baseColorFactor`.
   **Практическое следствие: сейчас в Godot бронза/дерево/камень будут выглядеть
   белыми/дефолтными, а не бронзовыми/деревянными.** Это не баг импорта (импорт
   технически прошёл чисто), а разрыв процедурный-материал → glTF PBR.
2. **Меши не разворачивались по UV** (материалы используют Generated/object-
   координаты, для рендера в Blender UV не нужны). Без UV нельзя запечь текстуру —
   это нужно будет добавить перед бейком (см. рекомендации).
2b. Emission-материал пламени маяка не проверялся отдельно на предмет
   `KHR_materials_emissive_strength` — вероятно, тоже нужно поправить руками.
3. **Draco-сжатие glTF недоступно** (`libextern_draco.so` не найден в этой сборке
   Blender) — экспорт идёт без сжатия. Для текущих полигональных бюджетов это не
   проблема (10–33 КБ на файл), но при большом количестве ассетов в реальной игре
   стоит собрать/поставить Draco отдельно.
4. **EEVEE (legacy) технически работает без GPU** через программный EGL/llvmpipe
   рендер, но на порядок медленнее Cycles CPU и шумит ошибками `EGL_BAD_MATCH` в
   лог на каждый кадр. Использовать не рекомендую. `BLENDER_EEVEE_NEXT` в этой
   сборке Blender 5.0.1 недоступен вовсе.
5. **Сервер выделяет процессу только 4 vCPU** (а не все 16 ядер хоста) — рендеры
   идут на этом ограничении; на выделенной машине с полным доступом к ядрам время
   рендера должно сократиться в разы (Cycles хорошо масштабируется по потокам).
6. Скелетной анимации и риггинга нет — только статичная геометрия (спайк не
   требовал анимацию).
7. LOD-уровней нет — один вариант меша на ассет. Для трёхпоясной 3D-карты (решение
   Р94: стратегический/региональный/детальный пояс) понадобятся минимум 2 LOD —
   упрощённый силуэт для дальнего пояса и текущий уровень детализации для ближнего.
8. Масштаб моделей — метры реального мира (человек ~1.8 м), экспорт в Y-up
   (`export_yup=True`, конвертация Z-up→Y-up сделана автоматически экспортером).
   Финальный масштаб в движке подбирать под сетку карты отдельно.

## Рекомендации для полного конвейера

1. **Обязательно добавить шаг «бейк перед экспортом»**: `Smart UV Project` на
   каждый меш → создать `Image Texture` нужного размера (256–512 px на ассет
   этого уровня детализации хватит с запасом) → `Bake` (Diffuse/Roughness/
   Metallic передачи в Cycles) → подключить запечённые текстуры в упрощённый
   Principled BSDF (только текстуры, без процедурных узлов) → уже такой материал
   экспортировать в glTF. Без этого шага вся «бронза с патиной» и «дерево»/
   «мрамор» не долетают до Godot.
2. Для эмиссии (пламя маяка, возможно светящиеся окна и т.п.) проверить, что
   Blender's glTF-экспортер добавляет `KHR_materials_emissive_strength` — при
   необходимости прописать `emissive_strength` вручную через API аддона.
3. Параллелить рендер по ассетам (blender-процессы независимы) — на машине с
   полным доступом к ядрам это даст кратный выигрыш по времени сборки библиотеки
   ассетов; сейчас `gen_all.sh` последовательный.
4. Библиотека частей (`common.py`) уже разложена так, что новые типы шлемов/щитов/
   оружия/кораблей/построек добавляются как новые функции-строители без
   переписывания камеры/света/экспорта — стоит формализовать её как настоящий
   пакет частей (JSON-каталог параметров вместо хардкода в `TYPE_PRESETS`), когда
   каталог юнитов (`docs/design/battle.md` §2.2, `UNIT_TEMPLATES.json`) будет
   использоваться как источник правды для генерации — тогда один и тот же JSON сможет
   параметризовать и баланс, и генератор ассета.
5. Установить/собрать Draco для Blender, если библиотека ассетов вырастет на
   порядки — сейчас не критично.
6. Добавить автоматическую проверку силуэта на читаемость при 24 px (даунскейл
   рендера + визуальный контроль) как шаг CI перед принятием ассета — сейчас это
   делалось вручную (см. раздел «Проблемы»).
